## Accepted decisions

| ID | Decision | Status | Rationale |
|---|---|---|---|
| D-001 | Provisionally use a history-preserving Harken fork pinned to a full commit SHA as the Windows substrate. | Superseded 2026-08-17 by D-049 | Phase 0B found that retaining Harken would duplicate the sensitive Android core while preserving little of the product's hard path. Keep it as a research reference only. |
| D-002 | Preserve the current local code as a Phase 0 prototype, not production base. | Accepted | Its requirements and tests are useful; its script architecture is not the long-term framework. |
| D-003 | Use a loopback-only FastAPI/Jinja web console as the provisional Windows experience; choose the phone UI in Phase 0B. | Superseded 2026-08-17 by D-049 | The proposed .NET MAUI foundation uses native Windows/Android UI and removes the local browser service from the production shape. |
| D-004 | Keep lexical-v1 as the baseline matcher. | Accepted for planning | Deterministic, local, explainable, and measurable before embeddings. |
| D-005 | Keep SQLite as the per-station store through Phase 2. | Accepted for planning | Fits local-first scope; federation does not use it as a global database. |
| D-006 | Default automatic-match retention is seven days; full text is retained only for topic matches or an explicit local Keep and author profiles remain off. | Accepted; extended by D-031 | Preserves a reviewable signal without accumulating unmatched content or profile data by default. |
| D-007 | Federation is absent from Phase 1 and Phase 2. | Accepted | Product value and boundaries must be proven first. |
| D-008 | Stop and deletion are separate actions. | Accepted | Prevents emergency response from silently destroying records. |
| D-009 | The first use case is read-only listening for standalone public relay messages with no recipient, group, reply, quote, or repost target. | Accepted | Closest technically real interpretation of "shouts in the dark"; makes structural filtering testable before semantic matching. |
| D-010 | Use hybrid discovery/tuned output: ephemeral awareness for all standalone shouts; automatic durable records and reports only for topic matches. | Accepted; extended by D-031 | Supports early exploration and later quiet operation; a separate explicit Keep may preserve one valid discovery. |
| D-011 | Compare Nostr public text notes with AT Protocol Jetstream in Phase 0A. | Accepted | A bounded comparison answers whether the more protocol-native Nostr surface or the broader AT stream provides more useful standalone shouts before Phase 1 commits. |
| D-012 | Retain the full public text of ordinary topic-matched shouts in encrypted local storage for seven days. | Accepted; extended by D-031 | A saved signal remains understandable and verifiable; explicit Keep supplies the only non-match persistence path. |
| D-013 | Require a manual passphrase unlock after every launch and lock again on STOP LISTENING. | Accepted | Keeps the usable key out of unattended startup and makes emergency stop close both network activity and plaintext access. |
| D-014 | Provide no passphrase recovery; lost-passphrase reset purges ciphertext and creates a new station key. | Accepted | Avoids escrow and bypass keys; seven-day records are disposable if the operator loses access. |
| D-015 | Require precision >= 0.85 and recall >= 0.60 before a matcher version may persist or report topic matches. | Accepted | Keeps durable alerts quiet and useful while the ephemeral waterfall supports wider exploration. |
| D-016 | Windows 11 and Android installations are independently operable stations; pairing is optional and never an operational dependency. | Accepted | Either station must remain useful when the other is absent, offline, stopped, deleted, or unpaired. Pairing may later add coordination without centralising custody. |
| D-017 | Target Android before considering iPhone. | Accepted | Android's user-visible foreground-service model is the closer fit for operator-enabled continuous listening; physical-device evidence still controls the operating claim. |
| D-018 | Permit Android off-screen listening only after explicit Start through a visible ongoing foreground service; STOP terminates it and prevents automatic restart. | Accepted | Provides useful coverage while keeping operation visible, voluntary, truthful, and immediately stoppable. |
| D-019 | Permit only a generic local Android `New signal found` match alert; require unlock for details and disable email, webhooks, and remote push in Phase 1. | Accepted | Alerts the operator without putting retained content or source evidence onto the lock screen or an external delivery service. |
| D-020 | Use `Cyber Space Radio` as the product name with `Public-source listening console` as the factual subtitle. | Accepted | Preserves the radio metaphor while making the actual public-source, software-only boundary visible wherever the name appears. |
| D-021 | Approve-disable Jetstream v2 US East, `relay.damus.io`, and `nos.lol` for a bounded local-client Phase 0A comparison, sampling Nostr first. | Accepted | Nostr kind-1 notes best fit the use case. Missing relay policies remain recorded caveats; strict limits, direct local access, no publishing, and immediate stop preserve the trial boundary. |
| D-022 | Phase 1 has no Cyber Space Radio backend and sends no listening data to the publisher. | Accepted | Each installation connects directly to public sources and performs filtering, retention, reporting, notification, deletion, and encryption locally. This sharply limits central privacy exposure and keeps each station independently deletable. |
| D-023 | Evaluate both approved Nostr relays concurrently and deduplicate their overlap locally by verified event ID before counting, display, matching, notification, or persistence. | Accepted | Two independent relays improve observable coverage; early deduplication prevents replicated Nostr events from appearing as multiple shouts or signals. |
| D-024 | On Nostr Start and reconnect, recover at most the preceding 60 seconds and show any longer interruption as a coverage gap. | Accepted | Covers brief disconnects without turning the listener into a historical collector; existing event-ID deduplication absorbs replay overlap. |
| D-025 | Show `Damus`, `nos.lol`, or `Both` on each Nostr shout and retain the delivering approved-source ID set for durable matches. | Accepted | Makes source provenance and relay overlap visible while one verified event remains one shout, activity increment, notification, and signal. |
| D-026 | Source-data deletion removes that source's provenance and deletes a signal only when no other observed source remains; exact signal deletion and full purge still remove complete records. | Accepted | A `Both` signal is one record with two valid delivery observations. Deleting Damus data should leave the independently observed `nos.lol` signal rather than erase unrelated provenance. |
| D-027 | Render Nostr signals locally by default and make external viewing a confirmed action using an operator-configured HTTPS viewer. | Accepted | Local review creates no third-party request. An explicit external action can disclose the event reference and browser connection metadata, so the destination must be visible and received content cannot configure it. |
| D-028 | Ship external Nostr viewing disabled with no configured viewer; expose the action only after deliberate local configuration. | Accepted | Prevents an optional third-party disclosure from becoming an accidental default or onboarding dependency. |
| D-029 | Suppress conservatively identified spam/flood events before the waterfall and matcher and expose only a non-identifying `Noise blocked` count by default. | Accepted | Keeps discovery usable without silently judging opinions or accumulating rejected content; rules are versioned, structural/repetition-based, and testable. |
| D-030 | Provide a memory-only Junk drawer for at most 50 valid spam-suppressed events or five minutes, with an exact-event `Restore once` action and no permanent rule learning. | Accepted | Enables false-positive inspection and recovery without creating a durable rejected-content archive; malformed and invalid events remain non-restorable. |
| D-031 | Allow explicit Keep for one message and opt-in `Keep future matches` per topic; kept records do not expire or suffer capacity eviction, while removal of their final keep reason starts a fresh seven-day expiry. | Accepted; extended by D-040 | A deliberate operator choice outranks automatic expiry. Topic-level keep is future-only by default so a settings change cannot silently retain historical content. |
| D-032 | Enforce an adjustable 100 MiB default hard durable-data capacity independently on each device, pruning expired then oldest unkept records and stopping new saves rather than evicting kept data. | Accepted | Prevents unbounded drive growth while preserving explicit Keep decisions and truthful local operation when protected data fills the allowance. |
| D-033 | A confirmed source-data deletion may delete sole-source Kept signals after a separate protected-item preview and named confirmation; multi-source Kept signals survive under remaining provenance. | Accepted | Keep prevents automatic loss but cannot override a deliberate deletion scope. Separate counts prevent an ordinary source cleanup from disguising protected-data removal. |
| D-034 | Bound the live waterfall to the newest 100 valid standalone shouts or ten minutes, whichever evicts first; successfully Kept items move to durable storage before volatile removal. | Accepted | Gives enough recent material for discovery while bounding memory and exposure. The commit-before-remove rule prevents a failed Keep from masquerading as a saved item. |
| D-035 | Show a 280-user-perceived-character waterfall preview with Unicode-safe local expansion of the complete accepted message. | Accepted | Keeps phone and desktop cards scannable without corrupting Unicode or turning expansion into an external lookup. |
| D-036 | Accept decoded public-message bodies only through 16,384 UTF-8 bytes; count larger bodies separately as `Oversized` and discard them before normalization, spam, Junk, waterfall, matching, notification, or persistence. | Accepted | The aggregate-only Nostr sample found a 195-byte median in both runs, a sub-800-byte 95th percentile, and a 4,585-byte maximum. A 16 KiB ceiling preserves generous room for legitimate narratives without treating resource rejection as spam. |
| D-037 | Accept an assembled incoming Nostr event-envelope message only through 65,536 UTF-8 bytes, independent of fragmentation; reject a larger message at transport intake before JSON event-field parsing where possible and report only `Oversized: envelope`. | Accepted | A small body can still arrive inside pathological wrappers or tag arrays. The envelope ceiling bounds intake and parser exposure while remaining four times the accepted body size. |
| D-038 | Make first-run topic selection a multi-select catalogue with no preselection, including relationships/dating, gossip/drama, friendship/family, other broad interests, custom creation, and `Skip and explore`; provide a skippable, replayable manual-topic tutorial. | Accepted | Gives new operators a useful starting point without silently deciding what they monitor. Editable local drafts and explicit enablement preserve control, while the tutorial teaches alternatives, exclusions, breadth, and retention. |
| D-039 | Use one unified Signals inbox with local topic/source/state filters. A shout matching multiple watches remains one row, count, notification, and encrypted content copy, with a set of inspectable per-watch decisions. | Accepted | A single inbox stays useful when some topics are quiet, while topic chips and filters preserve focus without duplicating content or alerts. |
| D-040 | Treat manual Keep and each keep-enabled matching topic as independent retention reasons on one signal. Any reason protects it; removing the final reason after confirmation begins a fresh seven-day expiry. Topic future-keep changes remain future-only unless a separate existing-signal action is previewed and confirmed. | Accepted | One record can match several topics, so a single retention flag would lose operator intent. Reason sets make protection and removal explainable without duplicating the message. |
| D-041 | Topic deletion transactionally removes that topic's definition, match decisions, and retention reasons after separately previewing other-topic survivors, manual-Keep survivors, ordinary deletions, and protected deletions. Signals with another match or manual Keep survive; those with neither are deleted. | Accepted | Deleting a topic should remove its data without erasing a still-valid signal or leaving an orphaned record. Separate protected counts make the destructive scope visible. |
| D-042 | Open every unlocked Signals session at `All topics`, newest first by initial observation. Retain filters, ordering, and scroll only in memory during that session; clear them on lock, STOP, restart, or reset. | Accepted | A stale filter must not make retained signals appear missing, and potentially sensitive viewing choices do not need durable storage. Stable first-observation ordering avoids old rows jumping when provenance or topic associations update. |
| D-043 | Mark a signal `Reviewed` only after successful unlocked local inspection and provide `Mark as new` as a reversible local metadata action. Review is shared across the one multi-topic signal and does not affect matching, notification, retention, ordering, or network activity. | Accepted | Automatic marking after real inspection keeps the inbox useful without treating a row impression or locked notification tap as review. Reversal supports interrupted or accidental inspection. |
| D-044 | Provide confirmed `Mark visible as reviewed` over an exact snapshot of all unique New signals in the current filtered result, without decrypting bodies or changing other behaviour. | Accepted | Makes a busy inbox manageable while a preview count, snapshot semantics, and no-op cancellation prevent the apparent scope from changing during the action. |
| D-045 | Give every streaming source an explicit 100-event intake queue and exponential reconnect backoff from 2 to 60 seconds with jitter; STOP cancels retries. | Accepted | The queue creates a measurable memory/backpressure ceiling and reconnect jitter avoids tight or coordinated retry loops. Overflow is an aggregate condition, not permission to open more connections. |
| D-046 | Use a random local signal ID and protocol-derived deduplication key; never use identical text as durable identity. | Accepted | Separate people may post the same words. Nostr event IDs and Jetstream AT URI/CID versions prevent cross-event collapse while still deduplicating relay delivery. |
| D-047 | Treat an authenticated Jetstream delete as authoritative over Keep and remove all retained versions of its AT URI immediately, leaving only a content-free audit/count. | Accepted | Respecting upstream deletion cannot depend on the local operator being present to approve it. Strict source, collection, and authenticity gates prevent unrelated delete messages from erasing data. |
| D-048 | Keep every new or edited watch preview-only until that exact frozen definition passes the accepted held-out corpus gate; invalidate promotion after any material edit. | Accepted | The global precision/recall promise must be attributable to the version that saves or notifies. Discovery highlighting and explicit Keep preserve exploration without presenting an untested custom watch as a reliable detector. |
| D-049 | Do not create the production Harken fork; use a greenfield .NET 10 MAUI solution as the next cross-platform foundation probe. | Proposed; Phase 0B physical gate | One shared C# behavioural core with explicit Windows/Android shells has lower parity and duplicated-security risk than Harken plus a separate phone core. The Windows primitive probe passed, but MAUI, device lifecycle, encrypted SQLite, notification STOP, and packaging remain unproven. |
